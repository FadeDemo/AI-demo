# Embedding 与逐篇检索

前一课已经能比较两组数字。现在让模型把文档和问题变成这些数字，再沿用相似度计算找文档。

本课做完，同一个检索入口就可以选择关键词或向量方法。两种方法都返回文档，下一课再用同一批问题比较结果。

## 1. 文本怎样变成向量

文本 Embedding 是模型根据文本生成的一条数值向量，也常译为文本嵌入。应用把文档和问题分别交给 Embedding 模型，取得每段文本各自的向量。

| 处理环节       | 输入     | 输出                   |
| -------------- | -------- | ---------------------- |
| Embedding 模型 | 一段文本 | 这段文本对应的一条向量 |
| 相似度计算     | 两条向量 | 一个相似度分数         |

检索时，应用沿用上一课的余弦相似度计算方法，逐一计算问题向量与每篇文档向量的相似度，再按分数排列文档。

Embedding 模型生成的向量包含与文本含义有关的信息。余弦相似度的数值等于两条非零向量夹角的余弦值，应用通过上一课的公式计算这个值，并用它估计问题与文档的相关程度。模型生成的向量和相似度计算方法需要配套，分数才有可能反映这种相关性。

选择模型时，先查看模型文档，确认它支持本次使用的语言，并明确支持文本检索用途。接着选几条问题，在自己的文档集合中运行本课的向量检索流程，查看排在前面的文档是否与问题相关。

文本向量中的大部分位置都用来参与计算，这类表示通常称为稠密向量，英文为 Dense Vector。第五课会介绍按词项组织、很多位置为零的稀疏表示。两者都可以用数字表示文本，生成方法与含义不同。

## 2. 文档与问题由谁处理

查询前，应用要先读取待检索的文档，生成并检查文档向量，再保存向量与文档编号的对应关系。本课把这个过程称为文档准备，读取文档的部分沿用第一课。

生成文档向量时，应用把每篇文档的标题、换行和正文合在一起，交给 Embedding 模型。这个调用模型生成向量的过程称为文档编码。每条向量都与原来的 `doc_id` 一一对应，检索后可以按编号回查原文。

用户查询时，应用只为本次问题生成查询向量，再与全部文档向量比较。文档内容没有改变时，可以复用已经生成的文档向量。

```text
文档准备
文档编号与标题正文 → 文档编码 → 文档向量与编号对应表

一次查询
用户问题 → 查询编码 → 查询向量
查询向量与每条文档向量比较 → 排名 → 按编号取回原文
```

把文档向量按行排成一张数字表，就是文档矩阵。50 篇文档、每篇 384 个数，对应 50 行、384 列。每一行的编号必须保留，不能只留下矩阵而忘了行与文件的对应关系。

本阶段允许将文档向量保存在内存中，一次准备后处理多条查询。跨进程保存和加载向量可以以后再做，不要求本课实现磁盘索引。

## 3. 文档和问题的向量要配套

问题向量要与文档向量计算相似度，两侧的编码方式需要配套。同一个模型有时对问题和文档采用不同前缀或指令，应用应按模型文档添加，用来标明输入文本的用途。

例如，Hugging Face 上发布的 `intfloat/multilingual-e5-small` 文本检索模型，模型卡要求检索问题使用 `"query: "` 前缀，文档使用 `"passage: "` 前缀，引号内保留末尾空格，非英文输入也采用这套规则。

`intfloat/multilingual-e5-small` 的单条输入序列长度上限为 512 Token。在模型卡的 Hugging Face Transformers 示例中，应用先调用配套的分词器（tokenizer），把带有前缀的文本转换成 Token 编号序列，并在分词时将超长输入截断至 512 Token。应用再将保留的输入序列交给模型编码，得到 384 维文本向量。[模型卡](https://huggingface.co/intfloat/multilingual-e5-small)

下面只展示输入转换，不代表已经执行了模型。

```text
原问题
请求一直没有返回怎么办？

交给这个 E5 模型的问题文本
query: 请求一直没有返回怎么办？

交给这个 E5 模型的文档文本
passage: 超时
请求超时后有限重试。
```

这些前缀属于该模型在检索任务中的用法，其他 Embedding 模型应按各自文档处理。如果 SDK 会自动添加前缀，应用就不应再手工重复添加。

例如，Sentence Transformers 的 Python 库用 `encode_query()` 为问题生成向量，用 `encode_document()` 为文档生成向量。模型配置中若保存了这两个方法各自使用的前缀，库会在编码前自动添加对应前缀。使用时，应先核对模型配置和库的说明，确认前缀是否由库自动添加，再决定是否由应用添加。[维护方的语义检索说明](https://sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

### 编码和检索要用的设置

前缀是模型对输入文本的一项要求。模型版本、向量维度和相似度计算方法也会影响两侧向量能否配套使用，应用需要按模型文档确认这些设置。

| 内容       | 本课需要确认的事情                                                       |
| ---------- | ------------------------------------------------------------------------ |
| 模型与版本 | 文档和问题来自同一个可兼容的模型版本或明确配套的两侧编码器               |
| 输入方法   | 问题与文档分别采用维护方要求的前缀、指令或用途设置                       |
| 维度       | 问题向量和每条文档向量包含的数值个数，都应等于配置声明的维度             |
| 相似度     | 按选定模型的建议采用余弦相似度、点积或其他方法。本课统一用余弦相似度检索 |
| 归一化     | 记录是否已把两侧向量变成单位长度，不能只凭数值范围猜测                   |
| 输入长度   | 标题、正文与前缀合在一起没有超过本次采用的输入限制                       |

本课推荐先选一个文档明确、支持中文检索的模型，并固定下来。前面的 E5 模型可作为入门候选，不要求必须采用它。若目标模型的主要用法不适合余弦相似度检索，应换用本课能正确配套的模型，或先说明需要怎样调整比较方法。

维度相同只是能够做运算。两个不同模型都输出 384 个数，仍不意味着它们在同一套表示中。更换不兼容的模型版本后，需要重新生成文档向量，不能把新问题向量直接放进旧文档矩阵。

## 4. 别在不知情时只编码了半篇文档

第一阶段已经讲过 Token。本课再次用到输入限制，但限制来自当前 Embedding 模型，不能沿用聊天模型的窗口数字。

本阶段先选择能完整编码的短文档。应用在送入模型前，用对应 tokenizer 检查完整输入长度；超过限制就明确报错并指出文档编号。人工选取适当的短资料后重新准备语料，不把自动截断当作已经完整编码。

本阶段以整篇文档为检索单位，要求完整正文都参与向量生成，便于回到原文检查检索结果。长文档的分段处理留到后续 RAG 实战。

模型来源、固定版本、输入方法、维度和长度检查方式应写入实验配置或记录。用本地模型时，首次下载与加载是环境准备；用服务时，认证信息只进入认证配置。默认自动化测试都使用测试替身，不在测试中下载模型或访问服务。

## 5. 数据少时逐篇计算就够用

所谓暴力检索或穷举检索，就是对每篇文档都算一次分数，然后选最靠前的 K 篇。为了让过程更容易理解，本专题也称它为逐篇检索。

```text
查询向量 q
→ 与 d1 计算余弦相似度
→ 与 d2 计算余弦相似度
→ 继续比较全部文档
→ 按分数降序排列，并列时按 doc_id 升序
→ 取前 min(K, 文档数) 篇
```

这会检查全部文档，不会因为某种近似搜索过程而漏掉高分向量。高分文档仍可能不符合人的相关性判断。模型表示与搜索算法是两件需要分别检查的事情。

文档编码完成后，应用应确认返回向量的条数与输入文档数一致，并检查每条向量的维度和有效性。应用还应保存每条向量对应的文档编号，以便检索后按编号回查原文。查询时，应用沿用第二课的输入检查，再进行相似度计算。

非空语料上的向量检索通常会返回 K 篇或全部文档，即使它们分数很低、内容没有答案。本课不新增相似度阈值或无答案检测。没有检索结果与没有答案之间的差别，下一课会单独记录。

## 6. 练习与验收

### 任务 1　接通两侧的 Embedding 编码

**目标。** 让文档和问题产生可比较的真实向量，并保留回查原文所需的编号。

复用第一课的文档记录和第二课的向量检查，增加文档准备与查询编码步骤。按所选模型的文档处理输入，记录模型版本、维度、前缀或指令、归一化方式及长度限制。文档超过限制时明确拒绝本次准备。

通过条件如下。

- 编码结果条数与文档数一致，向量和 `doc_id` 一一对应；问题采用对应的查询输入方式。
- 默认离线测试用能记录输入的编码替身，检查两侧用途、条数、编号对应、维度与非法向量的拒绝。检查失败后不进入相似度排序。
- 用目标模型手动为少量固定文档和问题生成真实向量，记录实际维度与运行方式，再准备整批语料。这份记录与预设向量测试分开。
- 在输入边界测试中，超长文档实际到达长度检查并被拒绝，模型编码步骤没有执行。不能用一个根本没有接入的编码器证明拦截有效。

### 任务 2　在同一入口增加向量检索

**目标。** 用户可以对同一个问题选择不同方法，得到相同字段的文档结果，为下一课批量评测作准备。

复用关键词检索入口，增加向量方法。查询走完编码、逐篇比较、排序和原文回查。默认结果按余弦相似度降序排列，并列时按编号升序。K 的检查沿用第一课。空查询或空语料返回空列表，不发起查询编码。

通过条件如下。

- 用同一个入口切换两种方法，返回字段一致，关键词方法继续通过原有回归测试。
- 流程测试从问题开始，使用预设查询与文档向量验证结果编号、分数、顺序、并列处理及 K 边界。测试不手动替程序补做查询编码或原文回查。
- 遇到不同维度、条数不符、零向量等错误时，应用应给出明确原因，并停止本次检索。
- 真实语料准备一次后，可连续检索多个问题；保留至少三个查询的两种结果。比较结果时回到原文核对，不要求向量方法一定领先。

### 知识检查

分别说明文档准备和一次查询由应用做了哪些事。解释相同维度为何不足以保证兼容，以及为什么一个没有答案的问题仍可能返回 Top-K 文档。
