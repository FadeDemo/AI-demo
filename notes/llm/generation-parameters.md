# 生成参数与采样

上一课解决了单次调用的容量问题：应用检查活跃输入与输出预算能否装进上下文窗口，并为本轮回答预留空间。但预算只规定模型最多可以生成多少，还没有规定模型怎样在这段空间里生成内容。

例如，同一份资料既可以用于“抽取三个固定字段”，也可以用于“提出十个不同标题”。前者希望输出稳定、便于验证，后者希望候选彼此有差异。如果应用完全不了解生成过程，就很难解释以下现象：

- 同一个请求重复运行，措辞或答案为什么可能不同；
- 参数不变、Prompt 不变，为什么仍不能保证逐字复现；
- 回答突然结束，究竟是模型正常完成，还是输出预算已经用完；
- 想要更多创意、更加稳定或更短的输出时，参数能帮到哪里，又不能替代什么。

这就是学习生成参数与采样的目的：不是为了给每次请求寻找一组神奇数值，而是为了让应用能够选择合理起点、识别生成结束状态，并通过对照实验判断某项设置是否适合具体任务。

LLM 通常按当前位置的候选 Token 分数逐步生成文本。模型每一步都必须选择下一个 Token：解码策略可以直接选择分数最高的候选，也可以从候选概率分布中采样。temperature、top-p 等参数会改变采样前的概率分布或候选集合；即使应用保留接口默认值，服务也会采用某种解码设置完成选择。生成参数还可以限制输出长度或设置停止条件，但不会更新模型知识，也不会验证事实。

## 1. 先判断是否需要调整

生成参数是一次模型调用的运行设置，不是模型能力本身。没有观察到明确问题时，可以先采用所选模型与接口的默认值，再用固定样本记录质量、稳定性、延迟和成本。只有当任务目标与当前表现之间存在可描述的差距时，才值得调整参数。

常见的调整理由包括：

- 抽取或分类结果波动过大，需要降低随机性并加强格式验证；
- 头脑风暴的候选过于相似，需要探索更多可能表达；
- 回答经常因输出上限被截断，需要重新分配预算或缩小任务；
- 需要比较模型、Prompt 或参数改动是否真的改善了目标指标。

参数调整应从任务目标和评测样本出发，一次只改变一个主要变量。若问题来自缺少事实、Prompt 含糊、Schema 不完整或应用没有验证输出，继续调采样参数通常不会解决根因。

## 2. 从候选分数到下一个 Token

在 LLM 流程中，“编码”和“解码”可能指不同层次的转换。分词器编码是把输入文本转换成 Token ID，分词器解码是把 Token ID 转换回可读文本。本课所说的“解码策略”不是后一种简单转换，而是模型生成内容时，根据候选分数决定以什么规则选择下一个 Token，并逐步组成输出序列。

模型先为候选 Token 产生分数，再转换成概率分布。解码策略根据这个分布选择下一个 Token，然后把新 Token 加入序列并重复过程。

一次生成包含很多次选择。即使开头相同，中间一次不同选择也可能让后续分布逐渐分叉。因此，不要把“设置相同参数”误认为“所有请求都保证逐字相同”。服务端更新、硬件并行和未固定的随机源也可能带来差异。

## 3. temperature 控制分布形状

temperature 通常译为“温度”，这个名称借用了统计物理中的概念。它不是某个候选 Token 的概率，也不代表模型对答案的置信度，而是把整组候选分数转换成采样概率时使用的调节系数。

可以把它理解为调节候选之间的差距：temperature 较低时，高分候选与其他候选的差距被放大，概率更集中，模型更容易反复选择少数高分候选；较高时，候选之间的差距被缩小，概率分布更平缓，原本概率较低的候选也更有机会被选中。因此，它适合在稳定表达与多样探索之间调节。不同模型服务对可用范围、默认值和边界值的处理可能不同，应以所选接口的文档为准。

它不是事实正确度旋钮：

- 低 temperature 可以稳定地产生同一个错误。
- 高 temperature 不会让模型获得训练后发生的新事实。
- 准确性仍依赖任务说明、可靠上下文、模型能力和验证流程。

## 4. top-p 限制候选集合

核采样（nucleus sampling）是一种先动态圈定核心候选集合、再按概率从中采样下一个 Token 的解码方法。这里的“核”指承载主要概率的核心候选集合，不是硬件中的计算核心。top-p 是核采样用来圈定这个集合的累计概率门槛；它不是某个候选 Token 的概率，也不是要保留的固定候选数量。

模型先把候选按概率从高到低排列，再从最高者开始累加；累计概率第一次大于或等于 top-p 时停止扩展，并保留此时的最小候选集合，最后只从这个集合中采样。累计概率不必刚好等于门槛：例如，候选概率依次为 0.5、0.35、0.1 和 0.05，top-p 设为 0.8 时，第一个候选的累计概率为 0.5，加入第二个后变为 0.85，已经越过 0.8，因此保留前两个候选。概率越集中，达到同一门槛所需的候选通常越少；概率越分散，候选集合可能越大。因此，top-p 控制的是一个会随当前概率分布变化的候选范围，较低的值通常会排除更多长尾候选。

temperature 调整整组候选的概率分布形状，top-p 则根据累计概率为候选集合划定边界。两者都会改变采样，初学阶段通常固定一个，只调整另一个并做评测。不能假设不同服务商对可用范围、边界值、默认值和能否同时设置有完全相同的行为，应以所选 API 文档为准。

就本课涉及的常见生成接口而言，temperature 和 top-p 都不使用负值；top-p 作为累计概率门槛也不大于 1。因此，应用可以先把负数视为无效输入，但不能据此写死完整取值范围：是否允许取 0、temperature 的最大值以及模型是否支持这些参数，仍由具体模型服务和接口决定。

## 5. 输出上限与停止条件

上一课从上下文预算角度把最大输出 Token 作为“要为本轮回答预留多少空间”；本课还要从生成结果角度判断模型为何停止。最大输出 Token 用来限制延迟、成本和失控长输出。上限太小会导致答案或 JSON 被截断；上限过大则只是允许模型生成更久，不代表模型一定会用完。

停止序列通常是应用代码调用模型 API 时，通过该接口的请求选项传入的一段或多段文本。它属于这一次调用的参数，与消息、输出上限等设置一起发送给模型服务；不是写进 Prompt 的任务指令，也不会永久修改模型。模型服务在生成过程中检查新输出；一旦输出匹配某个停止序列，就结束本次生成。它不是要求模型主动判断何时停止，也不是在回答末尾自动追加一段停止文本。

这种机制只按文本是否匹配来截停，不理解文本在当前任务中的含义。如果模型正在复述用户内容、生成代码或填写 JSON 字符串，而其中恰好出现同样的文本，也可能被提前截断。接口对于是否在响应中保留匹配到的停止文本，以及如何表示生成结束原因，可能有不同约定，应查阅所选接口的文档。结构化输出应优先使用专门的 Schema 能力并检查结束原因，不依赖脆弱的字符串截断。

## 6. 按任务选择第一组实验设置

不同任务对输出的要求不同，因此第一次测试时采用的设置也不必相同。这里的“第一组实验设置”是指：在还没有项目评测结果时，先根据任务目标确定想优先观察的输出特性，例如稳定性、多样性或完整性，再选择一组具体参数和输出预算，用固定样本运行并记录结果，最后决定是否调整。首次实验可以沿用接口默认值，也可以针对已经明确的目标只改变一个主要参数。不存在脱离具体任务、模型和接口的通用最佳值；第一组设置也不应未经评测就直接作为最终生产配置。

| 任务               | 首要目标   | 首次实验的设置思路                         |
| ------------------ | ---------- | ------------------------------------------ |
| 信息抽取、分类     | 稳定、合规 | 较低随机性，足够输出预算，Schema 验证      |
| 基于证据回答       | 忠于材料   | 较低随机性，明确引用与“不知道”，事实核验   |
| 标题或方案头脑风暴 | 多样性     | 适度提高随机性，一次生成多个候选后排序     |
| 代码修改           | 正确性     | 低到中等随机性，测试和静态检查比参数更重要 |
| 长篇创作           | 连贯与风格 | 给足预算，用大纲或分段生成控制结构         |

表中只说明第一次实验可以优先尝试什么，不提供可脱离具体模型和接口直接套用的固定参数值。最终选择必须由项目自己的样本和指标验证。

选择起点时不必一次引入接口提供的所有参数。所选接口还可能支持重复惩罚、随机种子、候选数量等设置；只有在需要解决明确问题且已经建立评测集时再逐项引入。参数越多，实验组合越多，也越难判断是哪项改动造成了结果变化。

## 7. 交互实验

配套实验把“这门课程很……”的下一个 Token 限定为六个候选，并固定使用下表中的教学分数：

| 候选 Token | 教学分数 |
| ---------- | -------: |
| 清晰       |     3.10 |
| 实用       |     2.45 |
| 系统       |     1.90 |
| 有趣       |     1.35 |
| 漫长       |     0.30 |
| 神秘       |    -0.20 |

教学分数是转换成概率之前的相对分数，不是候选概率；分数越高，只表示该候选在这组教学数据中的初始相对优势越大。这些分数由课程预先设定，不来自真实模型。

打开[上下文与采样实验](../../projects/llm-usage-lab/index.html)，选择“采样分布”。调整 temperature 与 top-p，观察候选概率、被 top-p 保留的集合和一次示意选择。

页面根据上述固定分数计算，不代表真实模型输出。通过实验应能区分“概率重新分配”和“候选集合截断”。

## 8. 练习与验收

本课继续扩展 [LLM Terminal Assistant](../../projects/llm-terminal-assistant/README.md)。任务 1 在项目的模型请求结构和提供方适配层中接入实验所选的生成参数，并通过显式执行的真实模型实验收集输出；任务 2 的结束状态处理和自动化测试也在该项目中实现。任务 1 的实验数据与结论、任务 3 的参数决策和知识检查属于书面记录。

### 任务 1：单变量对照（必须）

先让项目自定义的模型请求能够携带 temperature 或 top-p 中本次实验选择的参数，并由提供方适配层映射到所选接口实际支持的请求选项，不把实验值硬编码在适配层中。另一个参数在全部实验中保持相同；如果选择省略它并采用接口默认行为，则所有请求都必须以相同方式省略，并在实验记录中注明。

准备 10 个固定且彼此独立的输入，为所选参数设置三个值。对每组参数值都使用相同的 10 个输入，并把整组输入至少重复运行两遍；最低共得到 10 × 3 × 2 = 60 个输出。这里的“两遍”是重复执行同一批独立请求，不是进行两轮对话。每次请求都不携带其他实验请求的对话历史，模型、消息、输出预算和其他请求设置保持相同。

实验可以通过可重复执行的命令或专用入口批量运行，不要求逐条手工输入。真实模型调用可能产生费用并受到速率限制，必须与默认离线测试分开，由学习者显式执行。保存每次请求对应的输入编号、模型、完整参数设置、输出、运行序号和评判结果。

通过条件：提供方适配层正确传递所选参数，并有不访问网络的测试验证映射；三组配置之间只改变所选变量；每组都包含相同的 10 个输入和至少两遍结果；结论同时说明质量、稳定性和多样性，不能只展示一个最喜欢的样本。

### 任务 2：识别截断（必须）

用 fake 客户端分别返回结束原因为“正常完成”和“达到输出上限”的响应。应用应正常显示前者的文本，并在后者明确提示回答不完整。

通过条件：两个结束原因分支都有测试；判断依据是响应携带的结束原因，不依赖文本是否为空或结尾是否有句号。

### 任务 3：为任务写参数决策记录（必须）

为“资料摘要”和“标题头脑风暴”各选择一组参数起点，说明目标、风险、评测方法和何时重新调整。

通过条件：两个任务没有仅凭“temperature 越低越准确”得出结论；明确写出参数不能替代事实和 Schema 验证。

### 知识检查（必须）

解释 temperature 与 top-p 的区别、输出上限与上下文窗口的关系，以及相同参数为何仍不一定逐字复现。

完成后学习 [Prompt 设计](prompt-design.md)。
