# 结构化输出

本课以 JSON 作为结构化输出的示例格式。当模型结果要交给程序继续处理时，输出必须从“看起来像 JSON”升级为明确的数据契约。这份契约里，字段、类型和层级由 Schema 约束；取值范围、跨字段关系、权限和事实依据由应用再检查。

为了贯穿这些概念，本课使用一个简单场景：应用把一段学习资料交给模型，请模型生成一张包含标题、摘要和复习问题的学习卡片，再由程序展示或保存。程序期待收到的结果类似：

```json
{
  "title": "结构化输出的三层正确性",
  "summary": "程序需要依次检查 JSON 语法、数据结构和业务规则。",
  "questions": ["合法 JSON 为什么不一定符合 Schema？", "Schema 验证为什么不能保证内容真实？"]
}
```

如果模型漏掉标题、把 `questions` 字段生成为字符串而不是字符串数组，或者在摘要中编造了学习资料没有提供的事实，后续程序就不能安全地直接使用结果。下面以这张卡片为例，区分这些失败分别应在哪一层处理。

## 1. 三层正确性

| 层次     | 示例失败                         | 负责机制                     |
| -------- | -------------------------------- | ---------------------------- |
| 语法正确 | 缺引号、JSON 被截断              | JSON 解析器                  |
| 结构正确 | 缺 `title`、`questions` 不是数组 | JSON Schema 或类型模型       |
| 业务正确 | 题目为空、摘要失实、日期已过期   | 应用规则、数据库和进一步验证 |

合法 JSON 不代表字段齐全，Schema 通过也不代表内容真实。比如 `{"age": -500}` 可以同时是合法 JSON 和合法整数，但通常不符合业务规则。

## 2. 设计小而严格的 Schema

把上面的学习卡片写成 JSON Schema，可以得到：

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["title", "summary", "questions"],
  "properties": {
    "title": { "type": "string", "minLength": 1 },
    "summary": { "type": "string", "minLength": 1 },
    "questions": {
      "type": "array",
      "minItems": 2,
      "maxItems": 5,
      "items": { "type": "string", "minLength": 1 }
    }
  }
}
```

字段名应稳定、有业务含义；枚举只包含应用真正支持的值；默认拒绝未知字段可以尽早发现模型或版本偏差。不要为了避免失败把所有字段都设成可选字符串。

## 3. 原生结构约束与提示生成 JSON

“基于 Schema 的结构化输出”指模型服务允许调用方提交目标 Schema，并以此约束模型生成的业务数据的字段、类型和层级。这个术语不描述 REST API 响应体采用什么格式。接口可以始终返回一个合法的 JSON 响应信封，但信封中的模型输出仍可能只是“标题：结构化输出”这样的普通文本。整个接口响应虽然是合法 JSON，这段模型输出却不是应用需要的结构化对象。

如果模型服务提供这种能力，应优先使用。它通常比只在 Prompt 中写“返回 JSON”更能约束形状，但仍需应用验证：

- 服务支持的 Schema 子集可能有限。
- 安全拒绝、输出截断或网络中断可能没有目标对象。
- 字段内容仍可能违反业务规则或缺乏事实依据。
- SDK 升级后解析类型和错误类型可能变化。

如果模型服务不提供基于 Schema 的结构约束，应用可以在 Prompt 中要求模型生成 JSON 文本。模型内容此时通常以字符串形式返回，但这不表示任意自然语言正文都能解析成 JSON；这个字符串本身必须是一份完整、合法的 JSON 文档。

本课所说的“解析”，是把这份 JSON 文本交给 JSON 解析器，按照 JSON 语法解码成应用可以操作的数据值，例如对象、数组、字符串或数字。解析只判断文本是否符合 JSON 语法并建立对应的数据结构，不负责检查必填字段、各字段类型是否符合契约以及业务规则。在学习卡片场景中，解析得到数据值后，还要由 JSON Schema 验证它是否为包含约定字段的对象。

如果模型返回的是自然语言正文、带有代码围栏的 JSON，或者不完整的 JSON，解析就应明确失败。应用不应使用正则表达式从正文中捞取大括号，也不应把不合法的文本悄悄修补成 JSON。

## 4. 失败与修复策略

可选流程：

1. 原始生成只执行一次。
2. 解析和 Schema 验证。
3. 业务规则验证。
4. 根据失败类型选择直接拒绝或进行最多一次修复请求。
5. 修复仍失败时返回可诊断错误。

修复请求会增加成本，并可能改变原意。不能无限递归“让模型修复自己的输出”，也不能自动修复权限字段、金额或写操作参数等高风险内容。

## 5. 结构演进

Schema 是模型输出边界的数据契约：发起模型请求并验证结果的代码用它拒绝不合格的数据，验证之后负责展示、保存或继续计算的代码则可以依赖它所保证的结构。在学习卡片场景中，展示代码可以依赖验证结果一定包含非空的标题、摘要和约定数量的复习问题。

新增必填字段、重命名枚举或改变类型，都可能使原有的展示、存储等代码无法继续使用数据。因此，有必要在变更 Schema 时记录版本，并用固定样本测试旧数据和新数据的兼容性。

验证通过后，应把结果转换成应用内部定义的明确数据类型，也就是字段与 Schema 对应的类、记录或其他类型化结构。业务代码应使用这种已验证的数据，不要在各处直接访问任意字典。这样缺字段会在模型输出边界处失败，而不是运行到很远的位置才出现异常。

## 6. 练习与验收

本课继续扩展 [LLM Terminal Assistant](../../projects/llm-terminal-assistant/README.md)。任务 1 定义的 Schema 必须作为独立的 `.json` 文件保存在项目中，并为通过条件增加默认离线的自动化测试；具体目录可以按项目的语言和结构选择，但项目 README 必须能定位 Schema 文件和测试命令。任务 2 和任务 3 的验证流水线、修复逻辑与测试也保存在该项目中。

书面记录保存在本专题的[练习回答目录](answers/index.md)。对于任务 1，书面记录只需列出 Schema 文件路径，并说明是否允许额外字段以及如何拒绝重复来源 ID；不要在回答文档中重复粘贴完整 Schema。本课的知识检查也在同一回答文档中完成。

在以下任务中，应用会在调用模型前为每份学习资料分配一个稳定且唯一的来源 ID，并把 ID 和资料内容一起交给模型。`source_ids` 由模型返回，用来声明这张学习卡片依据了哪些输入资料；后续程序可以据此显示来源，并检查模型是否编造了不存在的来源。它不是资料标题、URL 或资料正文，也不由模型自行创建。

例如，应用向模型提供来源 `lesson-01` 和 `lesson-02`；如果卡片只依据前者，输出应包含 `"source_ids": ["lesson-01"]`。输出 `lesson-03` 即使通过了 Schema 验证，也因为该 ID 不在本次输入的允许集合中而无法通过业务校验。本练习只要求记录整张卡片的来源，不要求为摘要中的每句话建立精细引用。

### 任务 1：定义学习卡片 Schema（必须）

基于本课示例增加必填的 `source_ids` 字段，每个来源 ID 必须是非空字符串，数组至少一个元素且不能重复。明确是否允许额外字段。本任务只定义并测试 Schema，不实现应用的解析或业务校验代码。

通过条件：Schema 能拒绝缺字段、空标题、问题数量不足、错误字段类型和额外字段；标准 JSON Schema 使用 `uniqueItems: true` 拒绝重复来源 ID。

### 任务 2：建立验证流水线（必须）

实现由四步组成的验证流水线：先把模型输出按 JSON 语法解析为数据值，再按 Schema 校验结构，随后执行业务规则校验，最后把通过校验的结果构造成项目类型。前三个校验步骤分别返回可区分的错误类别；项目类型的字段与 Schema 保持一致，构造步骤只接收已经通过全部校验的数据。业务规则必须确认每个来源 ID 都属于本次模型输入的允许集合。错误日志只记录类别、字段路径和请求 ID，不记录完整模型输出。

通过条件：测试覆盖合法对象、坏 JSON、缺字段、错误类型、无效来源和被截断响应；只有全部验证通过的对象进入业务层。

### 任务 3：实现有限修复（必须）

在任务 2 的验证流水线之上增加一个独立的生成编排服务。该服务负责调用项目已定义的模型客户端，将正常完成的响应正文交给验证流水线，并根据验证结果决定是否发起一次修复请求。本任务不要求把该服务接入终端对话，也不要求新增命令行入口。

本任务只把“模型响应正常完成，但响应正文无法按 JSON 语法解析”定义为允许修复的失败。修复是向模型再发起一次明确要求返回完整、符合目标 Schema 的 JSON 的请求，不是用应用代码删除代码围栏、补引号或猜测缺失内容。Schema 校验失败、业务规则失败，以及被截断、被拒绝或请求未正常完成等响应状态，都不进入这条修复路径。修复后的正文必须重新经过任务 2 的完整验证流水线。

自动化测试应注入一个可按顺序返回预设响应并记录调用次数的模型客户端测试替身。这个替身只用于构造“首次解析失败后成功”和“两次都解析失败”等确定性场景；不要求修改项目现有的 fake 客户端，也不访问真实模型服务。

通过条件：测试证明首次生成合法时只调用模型一次；首次出现 JSON 语法解析失败且修复成功时总共调用两次；修复后仍无法解析时停止并返回可诊断错误；不允许修复的验证错误和响应状态不会发起第二次请求；修复成功的结果只有在通过完整验证流水线后才能进入业务层。

### 知识检查（必须）

分别举例说明语法、结构和业务正确性；解释原生 Schema 约束为何仍不能保证事实正确；说明无限修复循环的风险。
