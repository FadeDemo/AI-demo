# 流式输出与可靠性

流式输出让应用在完整回答结束前逐步收到事件。用户可以更早看到正文，但“已经显示一些内容”不等于“这次请求完整成功”。流可能在输出中途断开，也可能以输出截断或拒绝结束；应用需要根据明确的结束状态决定如何展示结果、是否继续处理以及能否重试。

本课围绕三个边界展开：增量内容何时可以展示，等待中的请求何时必须停止，以及失败后的重复执行会产生什么后果。目标是实现可观察、可停止、有恢复上限的请求流程，而不是让所有错误都自动重试。

## 学习前提与本课范围

先完成[模型调用与消息](model-calls-and-messages.md)、[Token 与上下文窗口](tokens-and-context.md)、[生成参数与采样](generation-parameters.md)、[结构化输出](structured-output.md)和[工具调用](tool-calling.md)。本课复用应用自定义的请求与响应、结束原因、输入预算检查、结构化验证流水线，以及连续工具处理与执行记录。

本课为供用户阅读的回答正文增加流式展示入口、超时与取消控制、有限重试，并用一个独立的内存草稿模拟器学习幂等。这里按输出的用途划定练习范围：回答正文用于展示；结构化输出中的数据需要交给程序验证；工具调用中的参数需要交给执行器校验。结构化数据和工具参数也可能分片返回，但本课只为回答正文接入流式处理。

本课的正文流式展示入口不向模型提供工具定义。工具调用和结构化生成采用本课的简化策略：继续使用先修课的完整响应，等本次模型响应正常完成后，再校验并执行工具，或验证结构化数据。这样可以复用已有的执行循环与验证流水线，集中学习正文的流式展示；它不是所有流式应用都必须采用的执行时机。本课会为工具调用流程接入取消检查，但不要求解析流式工具参数或把工具循环改成流式循环。

限流、并发和生产环境中的幂等存储用于理解可靠性的边界；它们不自动成为本课的必需实现。任务中的接口和事件名称由学习者定义，不要求复制某个 SDK 的类型或当前配套项目的类名。

## 1. 流不是任意字符串片段

应用通过所选模型接口向模型服务发送请求。启用流式响应后，SDK 会将服务陆续返回的信息解析为一系列事件。本课把这些尚未转换为应用协议的 SDK 事件称为“原始流”。原始流可能包含文本增量、工具参数增量、用量统计、结束状态、错误或心跳，具体种类取决于所选模型接口的协议。应用应先识别事件类型，只把文本增量中的正文用于展示，不能把每个事件都当作一段回答。

提供方适配层接收原始流，并把其中的事件转换为应用自己的事件协议。后续负责读取和处理这些应用事件的代码称为“消费者”，只依赖应用协议，不直接读取 SDK 事件。用于逐段展示回答正文的应用事件协议，至少需要表达以下三类事件：

| 应用事件 | 承载内容                         | 消费者行为                                     |
| -------- | -------------------------------- | ---------------------------------------------- |
| 文本增量 | 本次新产生的正文片段             | 按顺序追加并及时展示，不能重复展示累计正文     |
| 用量统计 | 输入、输出等 Token 用量          | 更新观测记录，不作为正文打印                   |
| 终止事件 | 已映射的结束原因和必要的结果信息 | 根据结束原因确定正常完成、截断、拒绝等最终结果 |

适配层应依据所选模型接口的完成信号和结束原因生成终止事件。某些模型接口可能先给出结束原因，随后才给出用量；应按其文档消费必要尾部事件，再结束应用流，不能因看到了一个结束字段就丢掉后续统计。用量可能缺失，应记录为未知，不能用零假装没有消耗。

消费者在终止事件前保持进行中状态。只有终止事件明确表示正常完成，才产生完整成功结果；正常完成也不代表正文的事实已经验证。输出上限导致的结束仍是不完整结果，非空文本、完整标点或迭代器自然耗尽都不能替代结束原因。没有终止事件就结束读取，应归为流中断。读取过程中发生异常时，应记录对应的失败类别。进入最终状态后，不再接收正文或继续后续操作。

回答正文可以边到达边展示；流中途停止时，已经展示的部分保留给用户参考，同时明确提示回答不完整或已取消。

结构化数据或工具参数也可能通过多个 SDK 事件逐步到达，应用需要累计这些事件携带的内容。即使累计内容已经可以按目标语法解析，也不能据此认定生成已完成。通用原则是依据所选模型接口的完成信号，确认要使用的数据或工具请求已完整，再进行相应验证；工具请求通过应用侧参数与权限检查后，才可执行。

单个工具请求生成完成、一次模型响应结束和整轮工具循环结束，是不同的完成边界。采用流式工具处理的应用，应按所选接口的契约与应用策略决定执行时机：如果协议允许在单个工具请求确认完整后执行，应用可以在校验通过后启动该工具；另一些应用会等待本次模型响应结束后再处理工具请求。两种方式都不需要先得到整轮工具循环的最终回答。

例如，OpenAI Responses API 将工具参数增量和参数生成完成表示为不同事件；[官方流式工具调用示例](https://developers.openai.com/api/docs/guides/function-calling#streaming)展示了这一过程。这里用它说明一种接口如何表达完成边界，实际实现仍应遵循学习者所选接口的契约。

本课采用“等待本次模型响应正常完成后再处理”的简化策略，复用先修课的工具执行和结构化验证边界。本课不要求新增结构化流消费者或流式工具执行器，也不以这些扩展作为验收条件。

## 2. 两种延迟

本课的逻辑请求是用户的一次输入所触发的处理流程，从应用接受输入、开始本轮处理时开始。一次逻辑请求可能包含重试，工具调用流程还可能包含多次模型调用。

在本课的正文流式展示流程中，“一次尝试”指应用为获取这次回答而发起的一次模型服务调用，包括建立连接和读取响应的过程。首次调用算第一次尝试；调用失败后重新发起请求，就进入下一次尝试。例如，首次调用失败后重试一次，是一个逻辑请求中的两次尝试。两次尝试之间的等待属于同一个逻辑请求，但不属于任何一次模型调用。

- **首个可展示内容延迟**：从逻辑请求开始，到消费者首次收到并交给展示层的非空回答文本片段。本课把这个测量口径记作 TTFT；它不是服务端生成第一个 Token 的内部耗时。
- **总耗时**：从同一次逻辑请求开始，到完成、失败或取消并完成本地资源清理。

TTFT 和总耗时使用同一个逻辑请求起点，重试不会重置它；发生重试时，两者都包含此前失败的尝试和重试之间的等待。可以另外记录各次尝试的耗时。

空片段、用量或心跳不能触发 TTFT。没有可展示正文的请求把 TTFT 记为缺失，而不是零。

计算 TTFT 和总耗时时，使用单调时钟。它提供用于测量时间间隔的读数，不会因系统日期或时间被调整而跳变；记录起点和终点的读数，再相减得到耗时。如果直接用两次系统日期时间相减，期间的时间调整可能让结果偏大、偏小，甚至为负。

流式展示减少了等待完整回答才能看到正文的时间，但不保证模型生成更快或请求总耗时更短。比较时必须保持起点、可展示内容的定义和终点一致。

本课验证延迟计算的自动化测试使用可控时钟和预设事件时序：由测试控制时钟读数，并按设定的时间点提供事件，无需实际等待。如果通过让测试程序实际等待一段时间（真实睡眠）来模拟事件延迟，线程调度和机器负载可能使实际等待超过设定时间，导致同一个测试有时通过、有时失败，也会增加测试运行时间。使用可控时钟，可以稳定验证计时起点、终点和计算结果。

## 3. 超时与取消

超时是等待预算耗尽；取消是用户主动要求停止。两者应有不同的结果类别，也不应都写成模型服务错误。

逻辑请求期限是预先设定的截止时刻，由本轮处理的开始时刻加上允许的时间预算确定。它用于触发停止；第 2 节的总耗时则记录实际经过的时间，包括停止后的本地资源清理。因此，总耗时可能超过设定的时间预算，不能把这个预算当作总耗时的严格上限。

| 等待边界     | 起止范围                                                                   | 计时与停止规则                                                                                                         |
| ------------ | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 连接超时     | 一次尝试建立连接的过程                                                     | 由传输层或 SDK 设置并映射为连接超时                                                                                    |
| 首事件超时   | 一次尝试开始，到收到首个有效流事件                                         | 到期停止该次尝试                                                                                                       |
| 流空闲超时   | 同一次流式响应中，从收到上一个有效事件到收到下一个有效事件                 | 每收到一个有效事件，就从接收时刻开始计算等待下一个有效事件的时长；达到空闲时限仍未收到，就停止本次读取并返回流空闲超时 |
| 逻辑请求期限 | 从本轮处理开始，到预先设定的截止时刻；重试等待和工具回传也占用这段时间预算 | 开始时确定截止时刻，重试不重置；到期发出停止信号并进入资源清理流程                                                     |

这里的“流空闲”指同一次流式响应暂时没有新的有效事件到达，不是不同流之间排队等待处理。首个有效事件到达前，使用首事件超时；收到首个有效事件后，才开始按流空闲超时限制后续事件的等待。流正常结束后，不再等待下一个事件。

首事件超时是一项等待限制：从本次尝试开始，在规定时间内仍未收到首个有效流事件，就停止该次尝试。TTFT 是观测指标：从逻辑请求开始，到首个非空回答文本片段交给展示层，记录实际经过的时间。首事件等待按每次尝试计时，TTFT 按整个逻辑请求计时；首次尝试若与逻辑请求同时开始，两者的计时起点可以重合。发生重试时，新尝试重新计算首事件等待时间，TTFT 仍从原来的逻辑请求起点计算。

适配层须声明哪些原始事件算作有效活动。如果用量或接口定义的心跳被认定为有效事件，收到它们就能结束首事件等待，但不能据此确定 TTFT，因为它们没有提供可展示的回答文本。例如，一次没有重试的请求在第 0 秒开始处理并发出请求，首事件等待上限为 3 秒；第 1 秒收到有效心跳，第 2 秒才把首段非空回答文本交给展示层。此时不会触发首事件超时，而 TTFT 为 2 秒。只有心跳而没有结果的流仍受逻辑请求期限限制。

程序等待下一个事件时，如果用户取消或等待时间耗尽，应结束当前等待。不能只在收到事件后才检查是否需要停止：如果服务端一直没有发送新事件，读取操作就可能一直等待，后面的检查也无法执行。无论采用同步还是异步实现，都需要使用所选传输层或 SDK 提供的超时、取消或关闭流的能力，让正在等待的读取操作能够结束。设置超时数值还不够，必须确保到期时能够中断当前的读取等待。

用户取消或等待超时时，消费者应停止处理后续流事件。如果底层读取仍在等待，应用应向提供方适配层发出停止通知，由适配层中断本次读取。

本次流结束后，提供方适配层应关闭流并释放读取所占用的资源；应用在完成本地资源清理后返回结果。正常完成、失败、超时和取消都需要执行这些收尾步骤，返回结果应明确标明本次处理的最终状态及相应原因。

应用应在发送下一次模型请求、执行每个尚未开始的工具前检查停止信号和逻辑请求期限；已完成的工具不因取消而被撤销，也不承诺远端已经停止计费。

本课要求阻止停止信号之后的新操作，不要求回滚已经发生的副作用、强行终止正在执行的任意工具或设计失败轮次的历史保存策略。先修课已实现的工具次数上限和预算检查继续有效。

## 4. 哪些错误可以重试

本课采用重新发送请求的简化重试策略：一次调用失败后，应用清理本次流，并在策略允许时复用同一份请求发起新的尝试。新尝试可能重新生成整份回答。本课仅在尚未展示正文时自动重试，避免把两次生成的内容拼成一份答案，也便于集中练习错误分类、退避和预算控制。

中断后的恢复还可以采用其他方式。如果接口支持恢复同一个响应的读取，应用可以重新连接并接收该响应的后续事件；Agent 也可以根据已有对话和已完成的操作记录继续剩余任务，必要时发起新的模型请求。因此，看到应用在中断后“接着做”，不能据此判断它是否恢复了同一次模型响应。本课不要求实现这两种恢复方式。

是否重试需要同时检查失败类别、剩余次数、剩余时间，以及是否已经展示内容或产生副作用。本课只对回答正文的流式展示流程实现自动网络重试，不自动重放工具循环或结构化修复流程。

下表是本课采用的教学策略，不是所有服务商的重试保证。真实适配层应按所选接口文档映射错误，不能将所有异常归为可重试。

| 失败类别                         | 本课策略                                                 |
| -------------------------------- | -------------------------------------------------------- |
| 连接失败、连接或读取超时         | 尚未展示正文且仍有预算时有限重试                         |
| HTTP 429 限流                    | 尚未展示正文时，根据服务端等待提示和剩余预算决定是否重试 |
| HTTP 503 服务暂不可用            | 尚未展示正文且仍有预算时有限重试                         |
| 其他服务错误                     | 只有适配层明确归入可重试类别时才允许重试                 |
| 认证、权限、无效请求或上下文错误 | 不原样重试，返回明确错误                                 |
| 截断、拒绝、Schema 或业务失败    | 不归入网络重试；结构化修复仍按先修课的独立策略处理       |
| 用户取消或逻辑请求期限耗尽       | 立即停止，不重试                                         |
| 已展示正文后流中断               | 不自动重试或拼接另一份答案，显示部分内容与不完整提示     |

指数退避让连续失败后的等待范围逐次增长，设置退避上限并加入随机抖动，降低多个客户端同时重试的概率。本课采用一种明确的规则：第一次重试的等待上界是基础等待时长，随后每次翻倍，但不超过退避上限；实际退避时长从零到当前上界之间随机选择。

服务端等待提示由适配层转换为等待时长；最终等待取随机退避时长与服务端提示的较大值。退避上限只约束客户端计算的退避，不能用它缩短服务端要求的等待。如果最终等待会用尽逻辑请求的剩余时间，直接停止，不提前重试。

最大尝试次数包含首次发送。例如，最多三次尝试允许首次发送加两次重试。重试前的等待和下一次模型调用共用本轮剩余的时间预算，开始重试不会延后截止时刻。到达逻辑请求的截止时刻时，无论正在等待重试还是进行模型调用，都应停止并进入清理流程。重试等待也必须能被用户取消。SDK 如果内置自动重试，应关闭或统一纳入预算，避免应用重试与 SDK 重试相乘。

同一逻辑请求的日志使用稳定的 `request_id`；`attempt` 从 1 开始，表示本课流式请求实际发送的第几次尝试。这两个字段是本课的应用观测约定，不是服务商协议字段。日志记录尝试次数、等待时长、结束或失败类别、TTFT、总耗时和可获得的用量，不复制完整 Prompt、正文、凭据或原始异常。失败尝试没有返回用量，不代表它没有成本。

## 5. 幂等性与副作用

纯文本请求重复执行可能增加成本并产生不同回答；有副作用的操作还可能重复创建、发信或扣费。超时只说明客户端没有及时得到结果，不证明服务端没有执行。因此，即使错误属于可重试类别，也不能据此认定写操作可以安全地再次执行。

幂等键由调用方为一次逻辑操作生成，重放同一操作时复用。执行端保存键、请求内容和已完成结果；同一键与同一内容再次到达时返回已有结果，不再次产生副作用。同一键却携带不同内容，应返回冲突，不能误把另一项操作当成已经完成。新的逻辑操作使用新键。请求日志 ID 用于关联处理流程，幂等键用于识别具体操作，两者职责不同。

本课用一个最小内存模拟器说明这个边界：调用方提交幂等键与草稿正文，执行端创建草稿并保存稳定的草稿 ID 和结果。再让传输替身在创建成功后丢掉第一次响应，调用方用同一键和正文重放，执行端应返回第一次的结果。这是组件练习，不需要模型生成写工具请求，也不需要发信、数据库或真实外部写入。

上述草稿模拟器将幂等键、请求内容和处理结果保存在内存中。本课只验证同一进程内依次重放操作的情况。生产系统还需要解决并发竞争、原子提交、进程崩溃、记录有效期和状态查询；这些不属于本课模拟器的验收。

工具已经执行、但最终回答丢失时，应用不应直接重新执行整轮流程。如果需要恢复，应用应先查询工具操作的执行状态，或依据执行端明确的去重契约，判断能否安全地重新发送相关操作。

## 6. 限流与并发

并发上限限制同时进行的请求数；速率上限限制单位时间内允许发出的请求量，两者不能互相替代。即使同时只发送一个请求，连续快速调用也可能触发速率限制。即使请求发送得不频繁，如果每个请求耗时较长，后续请求也可能在前面的请求结束前启动，使多个请求同时占用连接和内存。

排队需要容量和等待期限，不能用无限队列把拒绝转换成无限等待。计算请求发送频率时，应把重试产生的请求也计入。一次尝试失败后，应用应先关闭本次响应流并释放读取资源，再等待下一次重试。服务端可能分别限制请求量和 Token 量，具体维度、额度和恢复方式以所选服务的文档为准。

本课必修任务只处理单个逻辑请求及其有限恢复，不要求新增并发调度器、队列或 Token 速率计量。需要扩展时，应先声明容量、排队与拒绝策略，再单独验收这些能力。

## 7. 练习与验收

本课继续扩展 [LLM Terminal Assistant](../../projects/llm-terminal-assistant/README.md)。可运行实现、测试、配置和行为说明放在该项目中；知识检查属于书面记录，课程不依赖个人回答文件才能理解或完成。项目 README 须能定位正文流式展示入口、工具调用流程入口、取消方式、超时与重试配置，以及默认离线测试命令。

任务按下表顺序实施，测试随对应能力收尾，不另外编号为实现任务。

| 任务 | 新增能力                   | 复用的前置能力                    | 触发入口与可观察结果                                 |
| ---- | -------------------------- | --------------------------------- | ---------------------------------------------------- |
| 1    | 应用流协议、增量展示与计时 | 先修课的请求、结束原因、预算检查  | 正文流式展示入口按顺序展示正文并返回最终状态         |
| 2    | 超时、取消与清理           | 任务 1 的流、先修课的连续工具处理 | 流式入口可停止等待；工具调用流程停止后不再发起新操作 |
| 3    | 错误分类与有限退避重试     | 任务 1、2 的状态、时钟与截止时间  | 流式入口在预算内恢复，或带明确原因停止               |
| 4    | 操作去重与响应丢失后的重放 | 基础组件测试；本任务定义草稿操作  | 组件入口创建内存草稿，同键重放返回同一结果           |

自动化测试默认不访问网络、不需要凭据、不产生费用。事件流、时钟、等待器、随机数和错误均可用可控替身；流替身应能模拟等待中的读取，并记录读取、关闭和发送次数。应用流程测试必须调用终端使用的单轮处理入口；测试不能手动拼接正文、补做工具执行或自行再次调用模型来替代应用流程。组件测试可以直接调用事件映射或任务 4 的模拟器，但不能据此声称终端流程已经接通。

### 任务 1：接入回答正文的流式展示（必须）

为应用定义第 1 节的事件协议，并实现所选模型接口的流适配和 fake 流。通过正文流式展示入口逐段展示正文；这个入口不传工具定义，已有工具调用流程继续按先修课流程运行。发送前仍执行已有的输入预算检查，业务消费者不访问 SDK 原始事件。

用可控时序依次产生空正文、用量、三个非空正文增量和正常终止事件，再分别模拟输出截断、读取异常和缺少终止事件的流。记录最终结果、可获得的用量、TTFT 与总耗时。测试替身允许观察各个增量到达时的展示输出，证明应用没有等完整回答后才一次打印。

通过条件：

- 三个增量按顺序且只展示一次，用量和终止信息不混入正文；终止前仍为进行中，正常终止后才是完整成功。
- 输出截断、异常和无终止事件各有明确状态；已有正文保留并带不完整提示，不能仅因迭代结束就标记成功。
- 空正文与用量不触发 TTFT；无正文时 TTFT 缺失，用量缺失时记为未知；可控时钟下两类耗时符合第 2 节口径。
- 应用入口完成预算检查、读取和展示，适配层映射有组件测试；普通完整响应、结构化生成和既有工具循环的有效回归测试继续通过。

### 任务 2：让等待中的请求可以停止（必须）

为流式入口增加连接、首事件、空闲超时和逻辑请求总期限，类别按第 3 节区分。连接超时由适配层配置；其余等待边界由适配层或应用协调，但最终都返回应用可识别的原因。接入一种明确的终端取消操作，使等待首事件或下一事件时也能响应停止。

把同一轮的取消信号和总期限传入已有工具循环，在每次模型发送和每个工具开始前检查。正常响应已经包含合法工具请求、但执行尚未开始时，若信号已停止，就返回对应停止结果；不能通过隐藏工具定义或提前结束测试来证明工具被保护。

通过条件：

- 两个正文增量后读取异常，以及第一个增量后用户取消，均返回非成功状态并保留相应提示；取消类别与超时、服务错误分开。
- 分别让连接建立、首事件读取和下一事件读取保持等待，用受控调度实际触发对应超时；总期限测试持续产生有效活动，证明它不会被活动重置。每类测试的其他预算足够大，避免被别的限制提前挡住。
- 在尚无事件和已经收到一个增量后分别取消，等待中的读取都结束；测试不依赖真实睡眠，也不能再注入一个正文事件才让停止生效。
- 正常完成、异常、超时和取消均释放本次资源，关闭后不继续读取；通过替身的关闭记录和执行记录观察清理。
- 工具调用流程中，fake 模型返回合法已注册调用时触发取消或总期限；输入实际到达执行前停止检查，返回具体原因，目标工具执行次数为零，且不再发送后续模型请求。另用一次响应中的两个合法调用验证逐个检查：第一个 fake 工具执行后触发停止，第二个工具不执行，也不再发送回传请求。

### 任务 3：实现有预算的网络重试（必须）

只为正文流式展示入口实现第 4 节的错误分类、最大尝试次数、指数退避、等待上限与随机抖动。等待可被取消，每次发送和读取都受任务 2 的逻辑请求期限约束。适配层将服务端等待提示转换为应用可用的时长；README 说明如何处理所选 SDK 的内置重试。

用记录请求的 fake 客户端依次模拟超时、429、503 后成功，以及持续失败、认证失败、无效请求、已有正文后中断等场景。注入时钟、等待器和确定性随机数，不在测试中真实等待。

通过条件：

- 尚未展示正文的超时、429 和 503 在预算允许时按策略恢复；认证与无效请求只发送一次；正常结束、截断、拒绝和用户取消不进入网络重试。
- 最大尝试次数包含首次发送，持续失败到上限后停止；每次尝试复用本轮已通过预算检查的请求，不把失败尝试的部分结果追加成新的用户输入。
- 等待值符合退避、上限和注入的抖动规则，429 等待不早于已映射的服务端提示；等待会用尽总期限时不再次发送。等待期间取消也不再次发送。
- 已展示正文后中断只保留这一份部分正文与不完整提示，不自动重试；下一次尝试开始前，上一条流已经清理。
- 同一逻辑请求的计时起点和 `request_id` 不变，`attempt` 与实际发送次数一致；总耗时包含退避，日志含最终类别且不含测试 Prompt、正文或虚构凭据。所选 SDK 的重试配置不会额外产生未计数的尝试。

### 任务 4：实现内存幂等操作与响应丢失模拟（必须）

实现第 5 节的最小草稿模拟器：输入幂等键与非空正文，输出稳定的草稿 ID 和创建结果；内存中保存草稿及键对应的请求和结果。相同键与正文重放返回已有结果，同键不同正文返回冲突，新键可创建新草稿。

再实现一个传输替身：第一次调用确实进入模拟器并创建成功，但返回前模拟响应丢失；调用方随后复用相同键与正文。整个实验只操作测试内存，不接入真实写工具或终端工具注册表。

通过条件：正常首次调用生成一个草稿，空正文在创建前被拒绝；响应丢失后的两次调用共生成一个草稿，重放结果与已保存结果一致；同键不同正文返回可区分的冲突且不新增草稿；新键即使正文相同也可产生不同草稿 ID。测试须同时检查创建次数、已保存记录和返回结果，不能只因第二次调用没执行就声称幂等有效。

### 知识检查（必须）

以书面形式回答以下问题，并为每项举一个具体场景：

1. 为什么可展示正文、流的终止事件和完整成功是三个不同的判断？为什么收到第一个用量事件不能计算 TTFT？
2. 为什么只有总超时仍可能造成长时间卡住？用户取消与读取超时分别由什么触发？
3. 为什么 429、认证失败和已展示正文后的断流采用不同策略？重试次数与总期限分别限制什么？
4. 创建已经成功但响应丢失时，为什么再次执行可能产生副作用？调用方和执行端各承担哪部分幂等职责？
5. 并发上限与速率上限有什么区别？为什么重试也要计入容量与等待预算？

通过条件：能依据明确结束原因判断成功，区分等待超时与主动取消；指出重试不保证续接答案或没有额外费用；说明幂等需要执行端保存和复用结果，内存顺序模拟不能证明跨进程或并发安全；不把限制并发等同于限制请求速率。

- 任务 1 至 3 有由应用入口驱动的离线流程测试，事件映射另有组件测试；任务 4 有内存组件及响应丢失实验，不能宣称已接入真实写操作。
- 实现任务和知识检查的全部通过条件均有对应证据；运行项目规定的格式化、lint 与测试，并在 README 中说明配置和验证入口。
- 真实接口的流式映射如需手动验证，应由学习者显式运行并记录所选模型与接口；它可能产生费用，不能替代可控的失败、取消和重试测试。
- 流式工具参数、结构化流解析、并发调度、持久化幂等、已发生副作用的回滚和失败轮次的历史策略属于可选后续设计，不据此判定本课未通过。
