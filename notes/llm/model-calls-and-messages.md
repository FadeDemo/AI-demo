# 模型调用与消息

LLM 应用不是“把字符串交给模型”这么简单。一次调用至少跨过应用代码、SDK、网络服务和模型四层；模型返回的也只是一次生成结果，应用仍需判断它是否完整、合法、可信并适合展示或执行。

## 1. 一次调用的边界

```text
用户输入
  → 应用组装消息与参数
  → SDK 序列化并发送 HTTP 请求
  → 模型服务鉴权、排队并运行模型
  → SDK 解析响应
  → 应用验证、记录并展示结果
```

SDK 简化了认证、请求格式、流解析和错误类型，但不会替应用决定 Prompt 是否正确、工具能否执行、输出是否符合业务规则。网络请求成功只代表服务返回了响应，不代表内容事实正确。

调用链中的“SDK 层”是一个职责位置，不是某个特定产品。所选服务提供官方 SDK 时通常直接使用；没有官方 SDK 时，可以改用兼容主流消息协议（如 OpenAI 或 Anthropic 的 API 格式）的客户端库并指向相应端点，也可以自己用 HTTP 客户端写一个薄封装。无论由谁充当，这一层都负责序列化请求、发送请求和解析响应，业务代码只依赖自己定义的消息与响应结构，不直接绑定这一层的实现。

真实模型调用通常有费用并受速率限制。自动化测试应依赖自己定义的模型客户端接口，再用 fake 或 stub 返回固定结果。只有少量显式标记的集成测试访问真实服务。

## 2. 消息角色与来源

模型 API 通常把一条消息表示为包含角色和内容的结构化对象，这两个字段承担不同职责。例如，在 `{"role": "user", "content": "..."}` 中，`role` 标明消息在对话协议中的来源和功能，`content` 承载实际正文。因此，角色是请求结构中的协议信息，不是人为写在正文里的“用户：”或“系统：”标签。应用只能使用所选 API 支持的角色值，不能通过自定义一个听起来更高级的角色获得更高优先级。

请求中的消息数组由应用组装并发送给模型，调用方向只有“应用到模型”这一种。角色描述的是每条消息的内容在对话中由谁产生，而不是谁在发起这次调用。因此，请求数组中出现 `assistant` 消息，是应用把模型上一轮生成的回答作为历史回传，而不是“模型给模型发消息”；模型本轮返回的响应同样以 `assistant` 角色给出，应用可以把这条响应保存下来，在下一轮请求中原样放回。同理，`user` 角色标明内容来自最终用户，但把用户输入组织进请求数组的仍是应用代码。

除消息内容外，角色、消息顺序和工具调用 ID 等协议信息也会影响模型如何理解本次请求。它们分别承担以下作用：

1. 角色区分应用规则、用户输入、模型历史和工具结果。
2. 角色与消息在请求数组中的排列顺序配合：数组顺序表示对话先后，角色标明每条消息的来源和功能，两者共同构成多轮对话上下文。
3. 在工具调用协议中，`tool` 角色表明消息是工具执行结果；应用必须根据工具调用 ID，将每条工具执行结果关联到发起它的具体工具请求，不能仅按照角色或消息先后顺序进行匹配。

下表从典型生产者、协议作用和应用侧信任边界三个方面比较四种常见消息角色：

| 角色        | 典型生产者                 | 协议作用                                                             | 应用侧信任边界                                                               |
| ----------- | -------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `system`    | 应用的请求组装层           | 说明本次请求适用的总体任务、边界和输出规则                           | 内容应由应用构造；涉及权限、数据访问和副作用的安全边界须由应用代码校验并执行 |
| `user`      | 最终用户                   | 表达本轮任务并提供输入数据                                           | 按不可信输入处理                                                             |
| `assistant` | 模型，或应用回放的模型历史 | 表示模型生成的回答、拒绝或工具请求；在后续请求中可以作为对话历史回传 | 模型生成内容不天然可信                                                       |
| `tool`      | 应用的工具执行器           | 把特定工具调用的执行结果反馈给模型                                   | 执行器来源可识别，结果内容仍可能不可信                                       |

`system` 消息通常由应用在组装模型请求时，根据预先定义的规则或受控配置创建，用于说明本次调用的总体任务、行为边界和输出要求。它不是操作系统产生的消息，也不是处理后的用户输入，并且不会自动跨请求永久保存。

例如，Codex、Claude Code 这类 Agent 应用可以通过此类高层指令说明代码助手的职责和行为边界；但 Agent 应用传递给模型的完整上下文还可能包含工具定义、沙箱配置、环境信息和项目规则，这些内容不一定都属于单独一条 `system` 消息。部分模型 API 还提供 `developer` 角色，用来承载应用开发者指令；它是否存在、与 `system` 如何分工以及指令冲突时采用什么顺序，都以所选服务商的协议为准。

角色字段不能证明消息发送者的真实身份，也不会授予文件、数据库、网络或外部系统权限。用户身份由应用的认证机制确认，操作权限由应用的授权逻辑检查，工具调用则由应用执行器决定是否真正运行。

“角色优先级”不能代替应用的权限控制。即使 `system` 消息规定“不要删除文件”，应用也不能只依赖模型遵守这条指令。对于当前用户无权执行的删除操作，应用不应向模型提供相应工具；对于已经授权但风险较高的删除操作，应用仍应在执行前重新校验权限，并要求用户明确确认。

不同服务商可能使用不同字段名或新增角色。业务层应使用项目自己的 `Message` 和 `ModelResponse` 数据结构，由适配层完成转换，避免整个应用绑定某个 SDK 的响应对象。

## 3. 对话历史不是自动记忆

模型通常只看到本次请求中发送的内容。应用如果希望模型理解上一轮，就必须把必要历史重新发送，或把旧对话压缩成可追踪的摘要。

历史管理需要明确策略：

- 保留哪些 `system` 规则，不能在裁剪时丢失。
- 保留多少最近对话，何时摘要更早内容。
- 工具调用与工具结果是否成对保留。
- 用户是否可以删除会话，保存期限多长。
- 历史中是否包含敏感数据，是否允许再次发送给模型服务。

不要把无限追加消息称为“记忆”。它只是不断增大的上下文，最终会遇到窗口、成本和噪声问题。

## 4. 响应状态与结束原因

应用至少要区分：

- 正常完成。
- 因输出上限被截断。
- 模型请求工具。
- 内容被安全策略拒绝或过滤。
- 客户端取消、网络中断或服务错误。

不能只检查是否存在一段非空文本。例如，被输出上限截断的 JSON 可能非空但不可解析；模型提出工具调用时，文本字段可能为空却不是失败。

## 5. 凭据与配置

API Key 通过环境变量或密钥管理服务注入，不写进源码、示例命令、截图和日志。仓库可以提交只包含占位符的 `.env.example`，但不提交 `.env`。

模型名称、超时、最大输出和重试上限也应是显式配置。记录模型标识时，还要记录应用 Prompt 或评测集的版本，否则模型或 Prompt 改变后难以解释质量回归。

## 6. 练习与验收

### 任务 1：画出一次调用（必须）

选择准备使用的模型 SDK（若所选服务没有官方 SDK，则选择兼容协议的客户端库或自写 HTTP 客户端充当第 1 节的 SDK 层），画出从用户输入到终端展示的调用链，并标注凭据在哪里读取、消息在哪里组装、网络错误在哪里转换、输出在哪里验证。

通过条件：至少包含应用、SDK、模型服务和验证四层；没有把 SDK 描述成模型本身；明确指出真实调用的网络和费用边界。

### 任务 2：定义适配层数据结构（必须）

定义项目自己的 `Message`、`ModelRequest`、`ModelResponse` 和 `ModelClient` 接口。响应至少能表达文本、结束原因、usage 和工具请求，不直接向业务层暴露 SDK 原始对象。

字段无唯一正确答案，验收看行为；建议先查阅所选 SDK 官方文档中消息与响应对象的结构作为设计参考，再定义自己的结构。最小基线：`Message` 至少包含角色与内容；`ModelRequest` 至少包含消息列表；`ModelResponse` 的“文本”指模型生成的正文内容，可能为空（例如纯工具请求），响应结构应让正文与结束原因、usage、工具请求相互独立。基线之外的字段按需自由设计。

通过条件：使用 fake 客户端时，业务代码无需导入真实 SDK；更换模型服务时，预期只修改适配层和配置。

### 任务 3：完成两轮对话（必须）

实现两轮终端对话，记录实际发送的消息角色和顺序，但不记录消息正文。

通过条件：第二轮包含有效的 system 规则、第一轮 user 与 assistant 消息、本轮 user 消息；日志只记录角色、数量、长度或哈希等安全元数据。

### 知识检查（必须）

说明：模型为何没有自动跨请求记忆；HTTP 200 为何不等于业务成功；tool 消息为什么仍可能包含不可信指令。

通过条件：三个回答都能联系第 1 节「一次调用的边界」中的调用链，不以“SDK 会处理”代替应用责任。

完成后学习 [Token 与上下文窗口](tokens-and-context.md)。
