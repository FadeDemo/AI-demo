# 流式输出与可靠性练习回答

本文记录[流式输出与可靠性](../streaming-and-reliability.md)课程的知识检查回答。正文中的项目场景来自 [LLM Terminal Assistant](../../../projects/llm-terminal-assistant/README.md) 的离线测试，第五题另用明确假设的请求额度说明并发与速率的区别。

## 知识检查

### 为什么可展示正文、流的终止事件和完整成功是三个不同的判断？为什么收到第一个用量事件不能计算 TTFT？

收到可展示正文，说明应用已经有内容可以交给用户看，后续生成仍可能截断或失败。终止事件告诉应用这次生成以什么原因结束，其中也包括拒绝、达到输出上限等结果。只有结束原因明确表示正常完成，应用才能把本次响应按完整成功处理。句号、非空文本和迭代器自然耗尽都不能替代这个判断；正常完成也不保证回答中的事实正确。

本课的 TTFT 记录从本轮逻辑请求开始，到首个非空正文片段交给展示层之前经过了多久。用量事件提供 Token 消耗信息，不含可展示的回答正文，因此不能据此确定首个正文何时到达。整个请求都没有正文时，TTFT 应保持未知。发生重试时仍沿用本轮起点，把首个正文之前的失败尝试和退避等待算进去。

在[消费者测试](../../../projects/llm-terminal-assistant/tests/test_stream_consumer.py)的增量展示场景中，fake 先交付空字符串和用量，再交付三个正文增量，最后交付正常终止事件。应用应从第一个非空正文开始确定 TTFT，按顺序展示三个增量，再根据终止原因确认完成。另一个用例只有部分正文，随后迭代结束且没有终止事件。应用会保留已经展示的部分，并把结果记为缺少终止事件，不能按正常完成处理。

### 为什么只有总超时仍可能造成长时间卡住？用户取消与读取超时分别由什么触发？

总期限给整轮处理规定了一个截止时刻。如果预算较长，一次迟迟没有结果的连接或读取就可能耗掉大部分时间，用户仍会等待很久。因此还需要连接、首事件和流空闲等阶段性限制，让应用及时结束某个阶段的无进展等待。代码也必须能中断正在等待的读取；如果只在收到事件以后检查是否超时，服务端一直不发事件时，检查根本没有机会运行。

读取超时由等待预算耗尽触发，用户取消由用户主动要求停止触发。两者应保留不同的停止原因，都需要结束本次读取并清理相应资源。用户取消还应阻止本轮后续的模型请求和工具操作；读取超时能否重试，要继续检查失败类别、剩余预算和正文展示情况。已有部分正文可以保留给用户，但应标明回答不完整或已取消。取消不会撤销此前已经完成的工具操作。

项目的[终端入口测试](../../../projects/llm-terminal-assistant/tests/test_cli.py)把总期限设为 120 秒、首事件上限设为 3.5 秒，并让流保持在等待首事件的状态。测试通过受控调度触发首事件超时，检查应用能结束等待并显示对应提示，无需一直等到总期限耗尽。键盘取消用例则在读取仍未完成时送入 Esc 或 Ctrl+C，检查结果为用户取消，完成清理后还能继续下一问。

### 为什么 429、认证失败和已展示正文后的断流采用不同策略？重试次数与总期限分别限制什么？

本课把 HTTP 429 限流视为可能经过等待后恢复的失败。当正文尚未展示、次数和时间预算也允许时，应用可以结合退避与服务端等待提示再次发送。认证失败需要先解决凭据或访问资格问题，原样重发通常不能消除原因。正文已经展示后再断流，用户手里已经有一部分回答；本课选择保留这部分并提示不完整，停止自动重发。

这一选择与本课采用的重试方式有关。重新发送请求可能重新生成整份回答，不能保证接着上次断开的地方继续，也可能增加模型调用费用。即使某次失败没有返回用量，也不能据此认定没有消耗。把下一次生成直接拼到已有正文后面，还可能出现内容重复或前后矛盾。

最大尝试次数限制本轮能发送多少次，首次发送也计入。例如上限为三次，只允许首次发送加两次重试。总期限约束本轮处理可以继续到什么时候，准备请求、读取和退避共用同一个截止时刻，重试不能重置它。到期后进入清理流程，实际总耗时还会包含清理时间。

在[重试测试](../../../projects/llm-terminal-assistant/tests/test_stream_retry.py)的一个场景中，本轮预算为 6 秒，首次请求返回 429，并提示等待 5 秒；完成本次流清理时已经过去 2 秒，只剩 4 秒。即使尝试次数还有余量，应用也应以剩余时间不足结束，既不开始这次等待，也不再次发送。相邻用例验证了预算足够时可以在 429 后恢复，而认证失败或已有正文后的失败只发送一次。

### 草稿已经创建，但创建结果未送达调用方时，为什么重放可能重复创建？在这项业务操作中，调用方和执行端各承担哪部分幂等职责？

本题讨论应用发起的草稿创建操作。调用方是请求创建草稿的应用，执行端是实际保存草稿的组件或业务服务，返回结果包含草稿 ID 等信息。模型调用有自己的返回结果，可以包含回答正文或工具调用请求；本题关注的创建结果由业务执行端返回。

执行端可能已经保存草稿，创建结果却没有送达调用方。调用方只看到超时，无法据此确定创建是否成功。如果它重新发起一次没有去重保护的创建，执行端就可能再保存一份草稿。

调用方应为一次业务操作生成幂等键，在重放时复用原键和原请求内容。新的业务操作使用新键。执行端负责保存键对应的内容和已完成结果；同键同内容再次到达时返回已有结果，同键不同内容则拒绝并报告冲突。只在调用方记录一个键，无法让外部业务服务自动去重，实际执行写入的一端也需要落实这项契约。用于串联日志的请求 ID 也不能自动替代这套处理。

在[草稿组件测试](../../../projects/llm-terminal-assistant/tests/test_draft_store.py)中，测试代码扮演调用方，通过传输替身提交 `operation-1` 和正文。`InMemoryDraftStore` 扮演执行端，创建并保存草稿后将 `Draft` 返回给替身；替身随后抛出 `TimeoutError`，让调用方未能取得这次创建结果。测试代码再通过同一个替身复用原键和正文。两次请求都实际进入存储组件，但只创建了一份草稿，重放返回的 ID 和正文与首次保存的结果一致。

这项实验全部在本地内存中进行，没有调用模型或访问网络。它验证草稿创建操作的去重，不能保证模型生成请求不被重复执行或重复计费。实验也只覆盖同一进程内依次调用的情况；进程结束会丢失内存记录，多进程可能各自维护不同的记录，并发请求还需要避免同时把同一个键判为首次请求。因此，当前结果不能证明跨进程或并发安全。

### 并发上限与速率上限有什么区别？为什么重试也要计入容量与等待预算？

并发上限限制同一时刻有多少请求正在进行，速率上限限制一段时间内允许发出多少请求。请求完成得很快时，即使始终只有一个在途请求，也能连续发出很多次；请求耗时较长时，即使发送频率不高，也可能逐渐积累出许多同时等待的请求。

假设某服务每分钟最多允许 10 次请求，调用方每秒顺序发送一次，并在下一次发送前完成上一次请求。此时并发数始终不超过 1，一分钟却可以发出 60 次请求，仍然超过速率额度。把并发限制为 1，并不能替代每分钟的请求量控制。

重试同样会向服务端发出请求、占用处理资源，并可能消耗 Token，所以也要计入请求量和成本预算。沿用上面的假设，6 次首次发送加 4 次重试就已经占满 10 次额度。排队和退避也消耗本轮允许等待的时间，开始重试后仍应使用原来的截止时刻；队列还需要容量和等待期限，避免把无法及时处理的请求无限积压下去。
