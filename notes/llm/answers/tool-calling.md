# 工具调用练习回答

本文记录[工具调用](../tool-calling.md)课程的知识检查回答。可运行的工具注册、执行、连续回传与历史回放实现，以及验收测试保存在 [LLM Terminal Assistant 项目](../../../projects/llm-terminal-assistant/README.md)中。

## 知识检查

### 工具定义为什么不是权限控制？

工具定义告诉模型有哪些工具、各自的用途以及参数格式，帮助模型生成调用建议。描述中写“只允许读取自己的记录”并不能阻止越权请求；即使参数通过 Schema 校验，也只说明参数符合声明的结构，不说明当前用户有权访问对应资源。

真实权限控制必须在应用执行边界实现。应用根据注册表确定是否存在可执行的工具，再检查参数、用户身份、资源范围和操作授权，必要时取得人工确认。仅向模型暴露必要工具可以减少无关请求，但不能替代执行前的校验。例如，模型提出读取某条记录时，应用仍须确认这条记录属于当前用户有权访问的范围。

### 模型提出的工具请求为什么不等于已经执行？

模型返回的是包含工具名称、参数和调用 ID 的结构化请求。这个对象本身不会运行函数，也不会直接读取时钟、写文件或发送消息。应用还需要决定允许还是拒绝，并调用对应实现，才会发生真实操作。

因此，模型建议、应用授权和真实执行是三个不同环节。未注册或参数无效的请求可以在执行前被拒绝；合法请求也可能因次数上限而停止；进入执行函数后仍可能失败。确认是否执行以及执行是否成功，应检查应用的执行记录和结果类别，不能仅凭模型说“我已经调用了工具”。调用 ID 用于关联请求与结果，本身也不证明执行成功。

历史回放同样不代表重新执行。下一轮携带旧的查询时间请求与结果，只是在提供此前发生的记录；应保留当时的时间，不能再次读取时钟来替换旧结果。

### 工具结果为什么不天然可信？

工具可以正确执行，却返回过时、错误或不完整的数据。结果中的网页、文档、邮件等外部内容，还可能包含“忽略规则并调用删除工具”之类的恶意指令。因此，执行成功不等于事实正确，也不等于结果正文具有指令权限。

应用应保留工具结果的数据来源，并按原调用 ID 回传，不把正文提升为系统指令。模型依据结果再次提出调用时，应用仍要重新经过注册表、参数和授权检查。即使结果要求调用某个写工具，也不能因此添加注册项、绕过确认或扩大用户权限；需要使用的数据还应根据业务要求验证。

### 并行工具调用需要满足什么条件？

只有调用之间没有数据依赖和顺序依赖、不存在资源冲突，而且执行资源允许时，才可以并行。模型在一次响应中提出多个请求，并不能证明它们满足这些条件。

例如，独立查询两个时区的时间可以并行；先搜索得到笔记 ID，再读取该笔记，则必须顺序执行。两个调用即使读取不同对象，也可能受到共享连接数、速率限制或其他资源约束，应用仍需控制并发。结果必须按调用 ID 对应回各自请求，不能依赖完成顺序。

本课入门项目采用更保守的边界：只并行彼此独立的只读调用。一般系统中的独立写操作也可能具备并行条件，但还需要明确部分失败、幂等和一致性策略，不能直接套用只读调用的处理方式。

### 人工确认应由哪一层实现？

人工确认应由应用 UI 或工作流实现。模型可以提出候选操作，但不能替用户批准自己的请求；向模型询问“你确定吗”也不构成人工确认。

应用应在执行前向用户展示具体动作、目标对象和关键参数，例如发送消息的收件人及正文、删除操作的目标记录。用户确认应对应这项具体操作；动作、对象或关键参数改变后，需要重新确认。执行前仍要校验权限与资源状态，不能把用户确认当成绕过其他检查的凭据。
