# 结构化输出练习回答

本文记录[结构化输出](../structured-output.md)课程的书面回答。可运行的 Schema、验证流水线和验收测试保存在 [LLM Terminal Assistant 项目](../../../projects/llm-terminal-assistant/README.md)中。

## 任务 1：定义学习卡片 Schema

Schema 保存在 [`study-card.schema.json`](../../../projects/llm-terminal-assistant/schemas/study-card.schema.json)。它将 `title`、`summary`、`questions` 和 `source_ids` 全部定义为必填字段，并使用 `additionalProperties: false` 拒绝未声明的额外字段。

`source_ids` 至少包含一个非空字符串，并使用标准 JSON Schema 的 `uniqueItems: true` 拒绝重复 ID。确认每个 ID 是否属于本次输入的来源允许集合属于业务规则，由任务 2 的验证流水线实现，不属于任务 1 的 Schema 验收范围。

项目使用默认离线的自动化测试验证 Schema 本身合法，合法学习卡片能通过，并且缺少必填字段、空标题、问题数量越界、字段类型错误、额外字段、空来源 ID 和重复来源 ID 都会被拒绝。

## 知识检查

### 语法、结构和业务正确性

语法正确性只判断模型输出是不是一份完整、合法的 JSON 文档。例如下面的文本缺少右花括号，JSON 解析器会直接拒绝它：

```text
{"title": "结构化输出"
```

结构正确性判断解析后的数据是否符合约定的 Schema。例如下面的内容是合法 JSON，但 `questions` 是字符串而不是字符串数组，因此无法通过学习卡片 Schema：

```json
{
  "title": "结构化输出",
  "summary": "应用需要验证模型输出。",
  "questions": "为什么需要 Schema？",
  "source_ids": ["lesson-01"]
}
```

业务正确性判断结构合格的数据是否满足本次任务的实际规则。例如卡片返回 `"source_ids": ["lesson-03"]`，但本次输入只允许 `lesson-01` 和 `lesson-02`。这个值可以通过 Schema，因为它是由非空字符串组成的数组，却必须被应用的来源允许集合检查拒绝。

因此，三层检查解决的是不同问题：JSON 解析器负责语法，Schema 负责字段、类型和层级，应用规则负责当前业务上下文中的有效性。前一层通过不能替代后一层检查。

### 原生 Schema 约束为什么不能保证事实正确

原生 Schema 约束可以要求摘要是非空字符串、问题数量处于规定范围，并限制模型只能返回声明过的字段，但它不能判断字符串表达的事实是否得到输入资料支持。

例如，模型可以返回结构完全合格的摘要，却把资料中的日期、金额或因果关系写错；也可能声明一个确实存在于允许集合中的来源 ID，但摘要内容并不能由该来源推出。这些结果在字段和类型上都正确，事实仍然错误。

事实正确性需要应用结合原始资料进行检查，例如核对关键事实是否能在资料中找到依据、验证来源与结论是否对应，或者在高风险场景中交由人工复核。Schema 只能约束数据形状，不能充当事实验证器。

### 无限修复循环的风险

无限地让模型修复自己的输出会造成不可控的请求次数、成本和延迟；模型还可能反复产生同一种错误，或者在每次改写时逐渐偏离原始资料。对于金额、权限或写操作参数等高风险内容，反复生成也不能代替业务校验。

修复逻辑还可能掩盖真正的上游失败。例如输出因长度上限被截断、请求被拒绝、认证失败或网络中断时，继续要求模型修复 JSON 并不能消除失败原因，反而可能把不完整内容误当成可恢复数据。

因此，修复必须同时限制错误类别和尝试次数。一种有限修复策略是：只允许正常完成的响应在 JSON 语法解析失败后发起一次修复；Schema、业务规则和其他响应状态失败都直接返回可诊断错误。修复结果仍须重新经过完整验证，不能因为它是修复后的结果就降低检查标准。
