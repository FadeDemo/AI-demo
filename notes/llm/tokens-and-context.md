# Token 与上下文窗口

模型处理的基本单位是 Token，而不是字符、汉字或单词。tokenizer 按自己的词表与规则把文本转换成 Token ID；不同模型的 tokenizer 不一定相同，同一段文本的 Token 数也会变化。

## 1. Token 不是固定长度单位

一个汉字可能对应一个或多个 Token，英文单词也可能被拆成词根、空格和标点。代码、JSON、罕见字符和混合语言的比例通常与普通中文段落不同。因此，“一个 Token 等于几个字”只能用于粗略估算，不能作为硬性校验。

需要在客户端预判时，使用与目标模型匹配的计数接口或 tokenizer；请求完成后，以服务端返回的输入和输出 usage 为记账依据。模型或 tokenizer 版本变化时要重新验证估算误差。

## 2. 上下文是共享总预算

一次请求常见的预算关系是：

```text
system 消息
+ 对话历史
+ 本轮用户输入
+ 检索材料或工具定义
+ 协议和格式开销
+ 为输出预留的 Token
≤ 模型上下文窗口
```

![上下文窗口中输入与输出共享预算](assets/context-budget.svg)

`max_output_tokens` 一类参数通常限制本次最多生成多少 Token，它不是额外赠送的窗口。输入已经接近窗口上限时，必须减少输入或输出预留。

## 3. 长上下文的取舍

更长窗口能容纳更多材料，但不保证答案更好：

- 无关内容会稀释关键证据。
- 冲突、过期和重复材料会增加判断难度。
- 请求成本和首 Token 延迟通常随输入增大。
- 关键信息的位置可能影响模型使用效果。
- 更长的外部文本扩大 Prompt Injection 攻击面。

因此应优先选择相关、可引用、来源清楚的内容，而不是“能塞多少就塞多少”。RAG 课程会进一步讨论检索与切块。

## 4. 超预算时的明确策略

可选策略包括：

- 拒绝请求并告诉用户如何缩短输入。
- 保留 system 规则和最近消息，按已声明规则裁剪更早历史。
- 对旧历史生成摘要，同时保留摘要版本和原始消息引用。
- 减少检索片段数量或单片段长度。
- 降低输出上限，但不能低到必然截断约定结构。

不能随意从中间删除消息，也不能只截断工具结果的一半。工具请求和对应结果通常要成对保留，否则后续消息会失去语义。

## 5. 成本估算

若服务按输入和输出分别计价，一次请求的估算成本可以写成：

```text
输入成本 = 输入 Token / 计价单位 × 输入单价
输出成本 = 输出 Token / 计价单位 × 输出单价
总成本 = 输入成本 + 输出成本
```

价格会变化，应放在配置或成本表中并记录生效日期，不把示例价格写死在业务逻辑里。缓存输入、批处理或不同服务等级可能有不同价格，也要分开记录。

## 6. 交互实验

打开[上下文与采样实验](../../projects/llm-usage-lab/index.html)，选择“上下文预算”。调整 system、历史、用户输入、外部材料和输出预留，观察何时超过窗口。

实验的验收目标不是记住默认数字，而是能指出增加某一类输入后，哪一部分必须减少，以及为什么 system 规则不能像普通旧消息一样被任意裁剪。

## 7. 练习与验收

### 任务 1：比较真实计数（必须）

使用目标模型对应的计数方式，分别统计一段中文、一段英文、一段 JSON 和一段代码。保存原始字符数、Token 数、模型或 tokenizer 标识。

通过条件：四类输入都有结果；结论没有宣称固定的“字符换 Token”比例；其他人能根据记录复现计数环境。

### 任务 2：实现预算器（必须）

实现一个请求前预算函数，输入包含消息、工具定义、外部材料、窗口上限和输出预留，输出包含估算输入、剩余空间和是否允许发送。

通过条件：正常预算允许发送；总量等于上限时行为有明确约定；超过上限时不会调用 fake 模型客户端；system 和工具协议开销没有被遗漏。

### 任务 3：声明裁剪策略（必须）

为至少六轮的模拟对话写出裁剪策略，并用自动化测试证明 system 规则保留、最近消息保留、工具调用与结果成对处理。

通过条件：裁剪结果顺序合法；策略写入 README；不存在“数组太长就删第一个元素”这类无语义规则。

### 知识检查（必须）

解释：上下文窗口与输出上限的关系；长上下文为何不等于高质量；为什么服务端 usage 比客户端经验公式更适合结算。
